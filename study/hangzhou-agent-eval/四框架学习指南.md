## 二、OpenCompass（离线评测基座）

### 2.1 它到底是什么

一个**配置驱动的评测执行平台**：你把"模型 + 数据集 + 评分方式"写成配置，它负责批量推理、评分、汇总，产出可复现的结果。

- 仓库：<https://github.com/open-compass/opencompass>（7.6k★）
- 核心能力：100+ 数据集、HF/LMDeploy/vLLM 后端、API 模型、规则评测 + LLM-as-Judge、分布式/分级调度、CompassRank 榜单、VLMEvalKit 多模态、同门 AgentCompass。
- 学习入口：[Quick Start](https://opencompass.readthedocs.io/en/latest/get_started/quick_start.html) → [Workflow and Core Concepts](https://opencompass.readthedocs.io/en/latest/user_guides/framework_overview.html) → [配置化评测](https://opencompass.readthedocs.io/en/latest/user_guides/config_based_evaluation.html)

### 2.2 要掌握的核心概念（L3 必须能画出来）

1. **配置驱动**：`models` / `datasets` / `evaluators` / `summarizer` 用 mmengine config 组织；`read_base()` 继承组合。
2. **执行链路**：config → partitioner（任务切分）→ inferencer（批量推理）→ evaluator（评分）→ summarizer（汇总）。
3. **评分方式**：规则/答案抽取（多数客观题）vs **LLM-as-Judge**（主观题）。
4. **可复现**：`--work-dir` 下 `configs/`（配置快照）+ `predictions/`（逐样本输出）+ `results/` + `summary/`。
5. **生态外延**：CompassRank 榜单口径、VLMEvalKit、AgentCompass。

### 2.3 三级学习任务

**L1（1–2 天）**
- 安装（别装 `[full]`）+ CLI 跑 demo 数据集；
- 用 `--dry-run` 看任务划分，再 `--debug` 跑小样本；
- 看懂 `summary/` 的 CSV 每一列。

**L2（2–3 天）**
- 换自己的模型（API 或本地）→ 加一个中文数据集 → 跑多模型多数据集对比；
- 接一个**自定义数据集**（参考 [new_dataset](https://opencompass.readthedocs.io/en/latest/extension/new_dataset.html)）；
- 给主观任务配 **LLM-as-Judge**（参考 [llm_judge](https://opencompass.readthedocs.io/en/latest/evaluation/llm_judge.html)）；
- 做一次**重复评测**（参考 [repeated_evaluation](https://opencompass.readthedocs.io/en/latest/evaluation/repeated_evaluation.html)），回答"分数差多少才真实"。

**L3（3–5 天，可选）**
- 读源码：`opencompass/runners/`、`inferencers/`、`evaluators/`、`summarizers/`；
- 加一个自定义 evaluator 或 summarizer；
- 读 [贡献指南](https://opencompass.readthedocs.io/en/latest/faq/contribution_guide.html)，尝试提一个数据集/模型配置 PR。

### 2.4 面试高频 & 回答要点

- **Q：为什么评测结果不可比？** A：提示模板、few-shot、答案抽取、数据版本、judge 模型任一不同都会导致分数漂移，所以要固定配置快照并报告口径。
- **Q：LLM-as-Judge 怎么保证可信？** A：人工抽检一致性 + 位置/长度/风格偏差检查 + 规则兜底。
- **Q：OpenCompass 和 lm-eval 区别？** A：OpenCompass 更偏"平台 + 中文生态 + 榜单"，lm-eval 更偏"轻量执行 + 社区标准任务"。

### 2.5 常见坑

`[full]` 依赖冲突；API 限流；数据集下载；不同版本 config 格式变化；把"榜单分数"当结论。

## 三、SWE-bench（测试驱动判分）

### 3.1 它到底是什么

一个**从真实 GitHub issue 修 bug 的 benchmark + 官方判分 harness**：给模型仓库 + issue，让它生成 patch；然后把 patch 打进 Docker 环境跑测试，全部通过才算 resolved。

- 仓库：<https://github.com/SWE-bench/SWE-bench>（6.1k★）· 论文：[ICLR 2024 Oral](https://arxiv.org/abs/2310.06770) · 文档：<https://swebench.com/SWE-bench/>
- 关键数字：Verified **500** 题（人工校验可解）；Lite 300 题；另有 Multimodal / Multilingual 变体。
- 判分逻辑：**FAIL_TO_PASS（新测试必须过）+ PASS_TO_PASS（旧测试不能挂）** 同时满足 → resolved。

### 3.2 要掌握的核心概念

1. **instance**：`repo + base_commit + issue + patch + test_patch`（test_patch 隐含测试）。
2. **Docker 化复现**：每实例构建镜像（2024-06 起的容器化 harness）。
3. **F2P / P2P**：为什么是"修复 + 回归"双约束。
4. **resolved 率的局限**：测试覆盖偏差、环境成本、可被针对性优化、issue 泄漏。
5. **推理与判分分离**：`swebench infer`（agent 生成 patch）vs `swebench eval`（判分）。

### 3.3 三级学习任务

**L1（1–2 天）**
- 用 gold patch 跑通单实例判分，看懂 `results.json`；
- 读一个实例的测试文件，理解 F2P/P2P 具体是什么。

**L2（2–3 天）**
- `swebench infer` 用 mini-SWE-agent 生成预测 → 判分 → `swebench report`；
- 挑 5–10 个实例做子集实验（控制成本）；
- 做失败归因：定位失败 / 补丁错误 / 回归破坏 / 环境 / 测试问题。

**L3（3–5 天，可选）**
- 读 harness 源码：镜像构建、patch 应用、测试执行、日志解析；
- 了解 SWE-bench Verified 的构建方式（人工校验）与 Multimodal 变体；
- 尝试用其数据采集流程（官方目前暂停新实例查询支持）或给任务提 issue。

### 3.4 面试高频 & 回答要点

- **Q：resolved 率高就代表模型强吗？** A：不。要看测试覆盖（有些修复测试测不到）、环境差异、是否针对性优化、以及是否用未泄漏数据。
- **Q：SWE-bench 与 Terminal-Bench 区别？** A：前者"改代码修 bug"（仓库级 patch），后者"在终端把事做完"（环境操作的长程任务）。
- **Q：为什么 harness 必须 Docker？** A：依赖、系统差异会让同一 patch 结果不同；容器化保证可复现。

### 3.5 常见坑

换 patch 必须换 `run_id`（缓存坑）；镜像构建慢/占盘（≥120GB）；ARM 实验性；全量 Verified 成本高，先子集。

## 四、DeepEval（pytest 化评测 / CI 门禁）

### 4.1 它到底是什么

"LLM 应用的 pytest"：用 Python 写测试用例 + 指标断言，`deepeval test run` 跑，可进 CI 做回归门禁。

- 仓库：<https://github.com/confident-ai/deepeval>（19.2k★）· 文档：<https://deepeval.com/docs/getting-started>
- 指标族：GEval（自定义标准 LLM-as-Judge）、RAG（faithfulness/contextual precision/recall…）、Agent（Task Completion / Tool Correctness / Step Efficiency / Plan Adherence）、多轮、MCP、多模态；支持自定义 metric 与合成数据。

### 4.2 要掌握的核心概念

1. **LLMTestCase + assert_test + threshold**：把评测变成可断言的单测。
2. **指标选择**：端到端（黑盒）vs 轨迹/步骤级；不要堆指标，先 2–3 个关键指标。
3. **Judge 成本与校准**：阈值不是越严越好，要依据人工标注校准。
4. **CI 集成**：`deepeval test run` + 失败即阻断。
5. **Tracing/轨迹**：`@observe()` 记录 agent 决策路径，做轨迹级评测。

### 4.3 三级学习任务

**L1（1 天）**
- 跑通 README 的 GEval 示例；理解 score 0–1 与 threshold。
- `deepeval test run test_ai_agent.py`，看到 pass/fail。

**L2（2 天）**
- 写 10 条用例：3 类指标（正确性/相关性/Agent 轨迹）；
- 加一个真实 Agent 的端到端轨迹评测；
- 接 GitHub Actions/Jenkins，阈值失败阻断；
- 对失败用例做归因（模型 / Prompt / Judge）。

**L3（2–3 天，可选）**
- 自定义 metric（继承 Metric 实现 measure）；
- DAG 指标 / 合成数据生成；
- 与 Confident AI 平台或自建报告打通；
- 红队测试初步（注入/越狱用例）。

### 4.4 面试高频 & 回答要点

- **Q：评测和测试的区别？** A：传统测试是确定性断言；LLM 评测是非确定性，需要阈值、重复运行、方差、judge 校准。
- **Q：怎么防止 judge 偏差？** A：多 judge 投票、位置交换、人工抽检一致性、规则兜底。
- **Q：CI 里跑评测会不会太慢/太贵？** A：分层：快速规则子集每次跑，全量 judge 定期跑；缓存与并发。

### 4.5 常见坑

指标堆砌（噪声大）；阈值拍脑袋；judge 调用成本；默认读取 `.env` 导致 key 混淆。

## 五、Langfuse（观测 + 实验平台）

### 5.1 它到底是什么

开源 AI 工程平台：**trace 观测 + prompt 管理 + 评测（judge/代码评分/人工） + 数据集实验 + 看板**。基于 OpenTelemetry，可自托管。

- 仓库：<https://github.com/langfuse/langfuse>（36.8k★）· 文档：<https://langfuse.com/docs>
- 自托管：[Docker Compose](https://langfuse.com/self-hosting/deployment/docker-compose)（架构：Web + Worker + Postgres + ClickHouse + Redis + S3）
- 评测：[评估概览](https://langfuse.com/docs/evaluation/overview) · [Experiments via SDK](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk) · [CI/CD 实验](https://langfuse.com/docs/evaluation/experiments/experiments-ci-cd)

### 5.2 要掌握的核心概念

1. **数据模型**：trace → observation（span/generation/event）→ session；score 挂在 trace/observation 上。
2. **三种评分方式**：LLM-as-Judge、code evaluator（确定性）、人工标注。
3. **Dataset + Experiment**：把数据集版本化，跑实验对比 prompt/模型版本。
4. **可观测闭环**：线上 trace → 失败样本 → 数据集 → 回归实验。
5. **成本/延迟**：按 trace 看 token、费用、耗时，定位性能瓶颈。

### 5.3 三级学习任务

**L1（1 天）**
- 部署（Cloud 或 Docker Compose）→ 建项目/API Key → 打第一条 trace；
- 看懂 UI：Traces / Sessions / Scores / Datasets / Experiments。

**L2（2 天）**
- 接入一个带工具调用的 Agent（`@observe()` + `from langfuse.openai import OpenAI`）；
- 造一条失败 trace，练习"从 trace 定位失败点"；
- 建 dataset（≥5 条）→ 跑 experiment → 加 judge；
- 改 prompt 版本再跑，用 Compare Experiments 看差异。

**L3（2–3 天，可选）**
- 读自托管架构（ClickHouse schema、队列、S3 存储）与部署参数；
- 用 code evaluator 写确定性检查；配置 CI 实验；
- 做线上 case 采集回流与看板/告警；
- 对比 Cloud/Self-host 的权限、数据保留、成本。

### 5.4 面试高频 & 回答要点

- **Q：Observability 和 evaluation 的关系？** A：观测拿到真实失败样本与轨迹，评测把这些样本变成可回归的分数；两者构成"发现→沉淀→回归"闭环。
- **Q：为什么用 OTel？** A：避免厂商锁定、复用生态埋点、统一 trace 模型。
- **Q：线上评测怎么做？** A：在线 judge 打分 + 人工抽检 + 失败样本进数据集 + 定期回归。

### 5.5 常见坑

自托管资源不足（建议 4C16G/100GB）；容器启动顺序（ClickHouse 慢）；忘了 `flush()` 丢 trace；SDK 版本 API 变化快；judge 成本。

## 六、四者如何串成一个项目（W5）

**项目设定**：给一个「财税问答 Agent」建评测体系。

1. **OpenCompass**：建通用能力基线（知识/推理数据集 + 自定义财税数据集 + judge），产出"基座能力报告"。
2. **DeepEval**：把业务用例 pytest 化（10–20 条，正确性/合规/拒答），挂进 CI，产出"回归门禁"。
3. **Langfuse**：线上 trace 采集 → 失败 case 回流 dataset → prompt 版本实验对比，产出"线上闭环 demo"。
4. **SWE-bench**：作为"测试驱动判分"的方法论对照（不需要跑业务数据）——说明"为什么 Agent 评测要环境校验而不只是文本打分"。

**最终产出（简历可写）**：
> 设计并落地 XX 场景 Agent 评测体系：OpenCompass 建基座评测集与 judge；DeepEval 将 20 条业务用例 CI 化；Langfuse 打通线上失败样本回流与 prompt 版本回归。定位 X 类失败模式，推动版本指标提升 Y%。
