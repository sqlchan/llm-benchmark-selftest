# 五个测试集中文总览：它们到底测什么、怎么测

> 本目录是 `report/model-eval/` 的中文整理版：把 5 个代码/Agent 类基准的**题面翻译成中文**，并讲清楚「测什么能力、题目长什么样、判分器怎么判、分数怎么算」。
> 分册编号与原文一一对应；原文是证据来源（英文原题片段 + 官方链接 + 行号），本目录是中文导读。
> 本文所有数字都能在原文或分册里通过行内链接回溯；标注 `# TODO verify` 的是原文也未核实的项。

## 0. 五个测试集是什么关系

它们不是「同一件事的五个难度」，而是**五种不同的任务形态**，各自堵一个能力缺口：

| 编号 | 测试集 | 一句话定位 | 一句话「它堵的缺口」 | 分册 |
| :-- | :-- | :-- | :-- | :-- |
| 01 | **Terminal-Bench 4.0** | 真 Linux 终端里把工程任务做完 | 会写代码 ≠ 会把服务跑起来、把数据迁完、把 bug 修到行为正确 | [01-terminal-bench-4.zh.md](01-terminal-bench-4.zh.md) |
| 02 | **DeepSWE v1.1** | 真实仓库里做原创长程改动 | 改得对，还要**不弄坏原有上千个测试** | [02-deepswe-v1-1.zh.md](02-deepswe-v1-1.zh.md) |
| 03 | **NL2Repo-Bench** | 只给规格文档，从零生成整个仓库 | 「从 0 到 1」的架构与多文件工程能力 | [03-nl2repo-bench.zh.md](03-nl2repo-bench.zh.md) |
| 04 | **ProgramBench** | 只给二进制 + 文档，黑盒重建程序 | 大型项目重建的耐力与「逐字节对齐」的严谨 | [04-programbench.zh.md](04-programbench.zh.md) |
| 05 | **Automation-Bench v1.0.6** | 模拟 SaaS 里跑真实业务流程 | 会用工具、会读 SOP、**知道什么不该做** | [05-automation-bench.zh.md](05-automation-bench.zh.md) |

一句话记住区别：**TB4 看「事情最终有没有做成」；DeepSWE 看「新行为加上了、旧行为没坏」；NL2Repo 看「从零造出一个能过上游全部测试的仓库」；ProgramBench 看「从黑盒行为反推出一个几乎逐字节一致的程序」；Automation 看「在模拟办公软件里把业务流程的终态做对，而且没做多余的事」。**

**翻译覆盖范围（两层）**：

- **本导读版**：5 份分册逐题翻译了 **33 道真实题例**（01：9 道、02：7 道、03：5 道、04：5 道、05：7 道），即 `report/model-eval/01`–`05` 原文里收录的全部题例，每道给「英文原文 + 中文翻译 + 判分点 + 为什么这样判」。
- **全量版**：见 [`full/README.md`](full/README.md)——从官方仓库按 commit 拉取全部题面并逐题翻译：TB4 66 + DeepSWE 113 + NL2Repo 104 + Automation 806 = **1089 道题面**（ProgramBench 200 个实例没有自然语言题面，给的是二进制 + 文档，`full/04-programbench/` 提供 200 实例中文索引与说明）。

## 1. 任何测试集都可以拆成 5 个部件

理解这 5 层，后面所有差异都只是「参数不同」：

| 部件 | 作用 | TB4 | DeepSWE | NL2Repo | ProgramBench | Automation |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| **题面** | 告诉模型要做什么 | 一段自然语言指令 | 仓库 @ base commit + 行为描述 | 一份约 18.8k tokens 的规格 | 一个二进制 + 文档 | 一句业务请求 |
| **环境** | 模型能操作的世界 | 预装依赖的 Docker | 真实仓库 + 测试环境 | Docker + 测试镜像 | cleanroom（断网、二进制不可读） | 模拟 SaaS（47 工具 / 约 500 端点） |
| **Scaffold** | 把模型输出变成动作 | Harbor + mini-swe-agent / claude-code | Pier + mini-swe-agent | OpenHands 0.56 headless | mini-SWE-agent | `auto-bench` 的 function calling 循环 |
| **Verifier** | 判断做没做对 | 任务自带 pytest/脚本（独立容器） | 隐藏 test.patch 的 F2P/P2P | 上游 pytest 通过率 | 隐藏行为测试（pytest） | 程序化 end-state 断言 |
| **聚合** | 单题 → 分数 | resolve rate（k=5） | Pass@1 | 平均测试通过率 | Resolved 比例 / 平均通过率 | strict pass rate |

两个必须记住的结论：

1. **五个基准里没有一个是 LLM 当裁判**。全部是程序化判分：看容器终态、看行为测试、看上游测试、看数据库/邮件/表格的最终状态。所以「模型说做完了」不算数。
2. **分数不是模型能力本身**，而是「模型 + scaffold + 采样参数 + 判分口径」的联合结果。换 scaffold、换 toolset、换 k、换数据版本，分数都会变。

## 4. 分数怎么算（三个口径层次）

### 4.1 单题分

- **0/1 型**（TB4、DeepSWE、Automation）：verifier 全通过 = 1，否则 0。Automation 另有 partial credit（按断言比例，原文见分册 §5）。
- **0–100% 型**（NL2Repo、ProgramBench）：通过测试数 ÷ 总测试数。ProgramBench 另有 Resolved（=100%）与 Almost resolved（≥95%）两个派生指标。

### 4.2 整轮分（官方口径）

```
TB4         resolve_rate = 通过题数 / 66          （每题跑 k 次，官方 k=5，报平均 + 95% CI）
DeepSWE     Pass@1       = mean(reward_i), i∈113
NL2Repo     avg_pass     = mean(通过率_i), i∈104   （论文另报 Pass@1 count = 100% 的题数）
ProgramBench Resolved    = count(100%) / 200       （辅助：平均通过率、Almost ≥95% 比例）
Automation  strict_pass  = count(task_completed_correctly=1) / 600
```

### 4.3 三个「不可比」的轴（报告里必须写清）

| 轴 | 说明 | 典型陷阱 |
| :-- | :-- | :-- |
| **数据版本** | TB4 3.0 是 74 题、4.0 是 66 题；DeepSWE v1 vs v1.1 判分不同；ProgramBench 2026-10-22 更新过 | 「我跑出 52 分」没写 `@4.0.0` 就无法对照 |
| **scaffold / 采样** | 官方 TB4 用 claude-code 与 mini-swe-agent 分数不同；k=1 vs k=5 差很多 | 本地 k=1 结果直接对比官方 k=5 平均值 |
| **数据来源** | Automation 官方榜用**私有 held-out 集**，公开 600 题只能出 public-set pass rate；TB4 有 30/66 题被 Epoch 复核出评分缺陷 | 把公开集分数当官方榜分数引用 |

## 5. 本地只跑子集时，怎么读自己的结果

离线包实际可跑的子集是：TB4 36/66、DeepSWE 20/113、NL2Repo 16/104、ProgramBench 5/200、Automation 600/600。官方在 [README.md](../README.md#L38) 的提醒是：**子集评测只能做「同 harness 同子集」的横评，不能对官方榜**。

经验门槛（出自 [README.md](../README.md#L72) Q6）：

| 基准类型 | 冒烟 | 能看出方向 | 能粗略排序 |
| :-- | :-- | :-- | :-- |
| 0/1 型（TB4、DeepSWE） | 5 题 | 10 题 | 30 题以上 |
| 0–100% 型（NL2Repo、ProgramBench） | 5 题 | 10 题 | 方差更大，需更多 |

报告里必须写清四件事：**版本号 + 子集题号 + scaffold/参数 + 采样次数**。

## 6. 选型建议（按你要回答的问题选）

| 你想回答的问题 | 选它 | 原因 |
| :-- | :-- | :-- |
| 模型能不能独立把真实工程任务干完？ | **TB4** | 最接近真实终端工作，但最贵、争议最大（Epoch 评为 Flawed） |
| 模型在我们自己的仓库里改代码靠不靠谱？ | **DeepSWE** | 考「加新行为 + 回归不坏」，P2P 动辄上千，最像生产 PR |
| 模型能不能从一份规格从零做出一个完整项目？ | **NL2Repo** | 最纯粹的结构能力测试，但单题极慢 |
| 模型能不能在没有源码时仅凭行为重建程序？ | **ProgramBench** | 最硬核；难度极高，多数题只能是 Almost |
| 模型能不能正确使用办公/CRM 工具完成业务流程？ | **Automation** | 最便宜、最接近公司内部自动化场景 |

组合建议（预算有限时）：先跑 **Automation 的 simple 200 + 公开集抽 50 题**做冒烟（最便宜），再跑 **DeepSWE 20 题子集**看仓库改动能力，最后用 **TB4 5–10 题**验证端到端工程能力；NL2Repo / ProgramBench 单题成本高，适合少量抽测（各 3–5 题）。

## 7. 术语表

| 术语 | 中文解释 |
| :-- | :-- |
| **harness** | 官方评测框架/驱动，负责起环境、装 agent、收产物、跑 verifier |
| **scaffold / agent** | 把模型输出变成真实动作的执行器（如 mini-swe-agent、OpenHands、Harbor） |
| **verifier** | 判分器，独立于 agent 运行，通常是 pytest/脚本/断言引擎 |
| **F2P（fail-to-pass）** | 改动后必须从失败变通过的测试，代表「新行为」 |
| **P2P（pass-to-pass）** | 改动前就通过、改动后**不许挂**的测试，代表「旧行为」 |
| **reward** | 单题得分（0/1 或比例），聚合后得到整轮分数 |
| **resolve rate** | TB4 的整轮指标：通过题数 / 总题数 |
| **Pass@1 / Pass@k** | 每题跑 1 次 / k 次，通过即算；k 次取平均或取通过率 |
| **Resolved / Almost resolved** | ProgramBench：100% 通过 / ≥95% 通过 |
| **strict pass rate** | Automation：600 题中终态断言全过的比例 |
| **held-out 集** | 官方榜用的私有留出集，公开集分数不能直接对齐 |
| **reward hack** | 不解决问题、专攻判分器漏洞的取分方式（改测试、屏蔽 alert、劫持 TestMain…） |
| **cleanroom** | ProgramBench 的隔离环境：二进制只可执行不可读 + 断网，防止反编译抄源码 |
| **p95 latency** | 95 分位延迟，TB4 的零停机迁移题用它当性能预算 |
| **k=5** | TB4 官方每题重复 5 次取平均（66×5 = 330 trials） |

## 8. 常见误读（先看这 10 条，能少踩一半坑）

1. 把厂商模型卡自报的数字当「官方榜」——两者口径不同。
2. 拿 k=1 的本地结果直接对比官方 k=5 平均值。
3. 不写版本号（`@4.0.0` / `v1.1` / `1.0.6`）就横向比较。
4. 把公开集（Automation 600）分数当私有 held-out 官方分数。
5. 用平均通过率（0–100%）的结果冒充 Resolved（100%）。
6. 忽略 reward hack：TB4 30/66 题、DeepSWE 的改依赖/劫持测试都算「取巧得分」。
7. 以为测试文件对模型可见——五个基准里测试都在独立镜像/隐藏分支，模型看不到。
8. 以为本地子集能代表全量：子集有名有姓，必须写题号。
9. 把「写代码能力」与「终端操作能力」混为一谈（TB4 会挂很多纯代码强的模型）。
10. 忽略成本：ProgramBench 单题约 $36，TB4 整轮可达数千美元。

## 9. 分册阅读顺序

1. 先读本总览 §1–§3，建立 5 部件与能力地图。
2. 按你关心的能力读分册：仓库改动 → 02；端到端工程 → 01；从零造仓库 → 03；黑盒重建 → 04；业务流程 → 05。
3. 每份分册的 §6「真实题面（英中对照翻译）」是**原文题面的中文版**，可直接用来判断「这题考得是不是我们关心的能力」。
4. 每份分册的 §7「口径陷阱」决定你能不能把分数写进汇报。
