## 一、OpenCompass（7,559★）—— 先建立"评测平台"的全局观

- **仓库/文档**：[GitHub](https://github.com/open-compass/opencompass) · [文档](https://opencompass.readthedocs.io/) · [CompassRank 榜单](https://rank.opencompass.org.cn/home)
- **为什么先学**：JD 行 1/8 明确"OpenCompass 使用或贡献经验"；它是国内生态最全的一站式平台，一次能看清"模型配置 → 数据集配置 → 推理 → 评分 → 汇总"的完整链路。
- **要掌握的核心概念**（5 个）：
  1. 配置驱动的模型/数据集组织方式（config 即评测任务定义）
  2. inferencer：批量推理与并发/分布式调度
  3. evaluator：规则评分 vs LLM-as-Judge
  4. 结果汇总与 CompassRank 榜单口径
  5. 生态外延：VLMEvalKit（多模态）、AgentCompass（Agent 评测编排）
- **动手步骤**：
  1. 环境：`pip install -U opencompass`（先用轻量/API 模式，**别装 `[full]`**）
  2. 按官方 Quick Start 跑一个 API 模型的最小评测，先看 `--debug` 小样本结果
  3. 接一个**自定义数据集**（按 dataset config 格式），加一个 LLM-as-Judge 评分
  4. 查看输出目录的 summary/详情，与 CompassRank 上同类模型分数做差异解释
- **验收标准**：3 个模型 × 2 个数据集跑通；自定义数据集可复现；写 1 页"同一模型在不同数据集/提示下的分数差异"笔记。
- **常见坑**：`[full]` 依赖冲突；API 限流与并发参数；数据集下载与版本；不同版本 config 格式变化。
- **面试一句话**：*"我用 OpenCompass 跑通了 X 模型在 Y/Z 数据集上的评测，接自定义数据集时发现 config 与 evaluator 的差异会导致分数不可比，因此我固定了版本和提示模板。"*

## 二、SWE-bench（6,128★）—— 理解"测试驱动判分"的标准范式

- **仓库/文档**：[GitHub](https://github.com/SWE-bench/SWE-bench) · [文档](https://swebench.com/SWE-bench/) · [Verified 数据集](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified)
- **为什么第二**：JD 行 9/11/12 反复点名 SWE-bench（本地化落地）；它是 Coding Agent 的事实标准，也是"测试通过率 = 分数"的最佳教学样本。
- **要掌握的核心概念**（5 个）：
  1. instance = 仓库 + issue + 参考 patch
  2. Docker 化环境（可复现的关键）
  3. FAIL_TO_PASS / PASS_TO_PASS 判分逻辑
  4. resolved 率（以及它为什么失真）
  5. Verified 子集（500 题人工校验）、run_id 缓存机制
- **动手步骤**：
  1. 准备 Linux + Docker + 约 120GB 磁盘 / 16GB 内存 / 8 核（官方口径）
  2. 验证判分链路（用参考补丁）：
     ```bash
     git clone --depth 1 https://github.com/SWE-bench/swe-bench-tasks.git ./swe-bench-tasks
     swebench eval verified --gold -i sympy__sympy-20590 --run-id validate-gold --task-repo ./swe-bench-tasks
     ```
  3. 生成预测并判分：
     ```bash
     swebench infer verified -m <model> -o preds -w 8
     swebench eval verified -p preds --run-id my-run -j 8
     swebench report my-run -d verified
     ```
  4. 挑 3–5 个失败实例，分析"是没定位到文件、补丁错误、还是测试本身有问题"
- **验收标准**：gold 判分通过；agent 在若干实例上有结果；写清"resolved 率如何计算、会因何失真"。
- **常见坑**：**换 patch 必须换 run_id**（否则复用缓存结果）；镜像构建慢且占空间；ARM 机器实验性支持；测试泄漏风险。
- **面试一句话**：*"SWE-bench 的分数是 FAIL_TO_PASS + PASS_TO_PASS 双测试集都通过才计 resolved，所以它测的是'回归安全 + 新问题修复'；局限是测试用例偏差、环境复现成本和可被针对性优化。"*

## 三、Harbor + Terminal-Bench（6,672★ + 996★）—— 进入"真实环境 + 长程任务"评测

- **仓库/文档**：[Harbor GitHub](https://github.com/harbor-framework/harbor) · [Harbor 文档](https://harborframework.com/docs) · [Terminal-Bench 官网](https://www.tbench.ai/) · [terminal-bench GitHub](https://github.com/harbor-framework/terminal-bench)
- **为什么第三**：JD 行 4/9/11 要求"环境交互、终端/Computer Use、轨迹评测"；Terminal-Bench 是**连续 benchmark**（已迭代到 4.0），Harbor 是它的通用运行/沙箱框架，能把"环境 + agent + 判分"解耦。
- **要掌握的核心概念**（5 个）：
  1. Task 三件套：Dockerfile / 指令 / 隐藏测试
  2. oracle agent：先证明"任务本身是可完成的"
  3. resolution rate + cost + tokens 的联合解读
  4. 连续 benchmark 的版本/tag 策略
  5. 执行环境 provider（Modal / Docker 等）与多 agent harness 对比
- **动手步骤**：
  1. `uv tool install 'harbor[modal]'`
  2. oracle 验证（官方建议跑 5 次确认环境不 flaky）：
     ```bash
     uv run harbor run -d terminal-bench/terminal-bench@latest -k 5 \
         --agent oracle --n-concurrent 500 --env modal
     ```
  3. 换真实 agent：`--agent claude-code --model <model>`
  4. 挑一条轨迹，记录卡点步骤、耗时与 token 成本
- **验收标准**：oracle 5 次稳定通过；一条 agent 轨迹分析（失败点 + 成本）；能解释不同 harness 分数为何不能直接横比。
- **常见坑**：Modal 额度；oracle flaky 优先怀疑环境；任务持续更新，跨版本比较要固定 tag；不同 harness 不可比。
- **面试一句话**：*"Terminal-Bench 用 Docker 环境 + 隐藏测试算 resolution rate；我会先跑 oracle 5 次验证环境，再看 agent 轨迹定位卡点，而不是只看总分。"*

## 四、Langfuse（36,809★）—— 补上"平台/可观测"这条线

- **仓库/文档**：[GitHub](https://github.com/langfuse/langfuse) · [文档](https://langfuse.com/docs)
- **为什么第四**：JD 行 14 明确要求"Langfuse 构建自动化评测流水线 + 全链路观测"；行 21 要求"评测系统全生命周期"。它是"trace → dataset → judge → experiment → 看板"闭环的最佳载体。
- **要掌握的核心概念**（5 个）：
  1. trace / span / session 数据模型（基于 OpenTelemetry）
  2. prompt 管理与版本对比
  3. dataset + experiment（离线回归）
  4. LLM-as-Judge / code evaluator / 人工标注三种评分方式
  5. 线上 trace 采集与失败案例回流
- **动手步骤**：
  1. 用官方 self-hosting 的 Docker Compose 方式本地起服务
  2. Python/JS SDK 接入一个最小 Agent，产生 2 条 trace（成功 + 失败各一）
  3. 建 dataset → 跑 experiment → 配一个 LLM judge
  4. 对比两次 prompt 版本的指标差异
- **验收标准**：可自托管运行；2 条 trace 可查；1 次 dataset experiment 带 judge 分数；能讲清"评测结果如何回流到 prompt/数据"。
- **常见坑**：自托管资源与版本兼容；OTel 埋点字段缺失导致 trace 断链；judge 成本；数据保留策略。
- **面试一句话**：*"我用 Langfuse 把一次 Agent 调用做成 trace，再把失败 case 沉淀进 dataset，用 judge + experiment 做版本回归——这就是 JD 里说的'线上 case 采集录制 + 自动化评测流水线'。"*

## 五、OpenJudge（1,009★）—— 把 Rubric / Grader 方法论落地

- **仓库/文档**：[GitHub](https://github.com/agentscope-ai/OpenJudge) · [文档](https://agentscope-ai.github.io/OpenJudge/) · [PyPI](https://pypi.org/project/py-openjudge/)
- **为什么第五**：JD 行 9 要求 Rubric/Grader/Verifier；行 12 要求"能力维度→任务→数据→评分标准"；行 13 要求把业务规则沉淀为可规模化 Rubric/Checkpoint。OpenJudge 的 50+ grader 与 rubric 自动生成，是这条能力的现成教具。
- **要掌握的核心概念**（4 个）：
  1. grader 分类：通用 / Agent（tool selection、memory、plan、trajectory）/ 多模态
  2. rubric 生成：zero-shot（无标注）与 data-driven（少量标注）
  3. GradingRunner + aggregator（加权汇总）
  4. grading → reward 信号（对接训练/优化）
- **动手步骤**：
  1. `pip install py-openjudge`
  2. 跑 README 的最小示例（RelevanceGrader），理解 score/reason 输出
  3. 用 SimpleRubricsGenerator 为一个真实业务场景生成 rubric
  4. 用 GradingRunner 跑 10 条样本 + WeightedSumAggregator 汇总
  5. （可选）接 Langfuse，做线上评测
- **验收标准**：一个业务场景（如客服/财税咨询）的 5 条可复用 rubric + 对应 grader + 评分报告；能说明 rubric 与人工评分的一致性如何校准。
- **常见坑**：项目较新（0.2.0 有一次不兼容迁移：`rm-gallery` → `py-openjudge`）；judge 模型选择影响一致性；rubric 过细会导致过拟合。
- **面试一句话**：*"我把业务规则拆成 5 条 rubric，用 OpenJudge 生成 grader 跑批量评分，再抽 20 条人工复核校准一致性——这正是 rubric 类评测落地的关键。"*

## 六、DeepEval（19,214★）—— 把评测变成工程里的"单测"

- **仓库/文档**：[GitHub](https://github.com/confident-ai/deepeval) · [文档](https://deepeval.com/docs/getting-started)
- **为什么最后**：JD 行 5 要求测试用例自动生成、测试结果评估体系；行 17 要求"编译测试 + 规则验证 + 模型裁判 + 人工评审"。DeepEval 的 pytest 风格最适合把前面学到的方法固化成 CI 里的回归用例。
- **要掌握的核心概念**（4 个）：
  1. LLMTestCase 与 assert_test（pytest 集成）
  2. 指标族：GEval 自定义标准、RAG（faithfulness / contextual precision…）、Agent（Task Completion / Tool Correctness / Step Efficiency / Plan Adherence）、MCP、多轮
  3. `deepeval test run` 与 CI/CD 集成
  4. 轨迹/tracing 与合成数据生成
- **动手步骤**：
  1. `pip install -U deepeval`
  2. 写第一个 GEval 用例（README 的 Correctness 示例），`deepeval test run test_ai_agent.py`
  3. 加 3 个 Agent 指标，跑一个真实 Agent 的端到端轨迹
  4. 接入 CI（GitHub Actions/Jenkins），阈值失败即阻断
- **验收标准**：10 条用例覆盖 3 类指标；CI 中可回归；对失败用例能做"模型/Prompt/Judge"三类归因。
- **常见坑**：judge 成本与调用次数；阈值需要校准（不是越严越好）；指标不要堆砌（先选 2–3 个关键指标）；默认会读 `.env`。
- **面试一句话**：*"我把 LLM 评测写成 pytest 用例，用 GEval 做正确性、用 Agent 指标做轨迹评估，再挂进 CI，阈值失败就阻断发布——评测从此是工程门禁而不是一次性报告。"*
