## 〇、先建立一个统一抽象：评测系统 = 四要素

四个框架虽然技术栈完全不同，但都可以拆成同一个四要素模型：

```text
             ┌─ 数据/任务（dataset, task spec, test case, event）
             │
评测系统 = ──┼─ 执行环境（model/inferencer, docker container, pytest, trace/queue）
             │
             ├─ 判分函数（evaluator, grading, metric, evaluator/rule）
             │
             └─ 结果存储与聚合（results/summary, report, test run, ClickHouse+Postgres）
```

| 要素 | OpenCompass | SWE-bench | DeepEval | Langfuse |
|---|---|---|---|---|
| 数据/任务 | dataset config（reader/prompt template） | SWEbenchInstance / TestSpec | LLMTestCase / EvaluationDataset | trace/observation 事件、DatasetItem |
| 执行环境 | 模型实例 + inferencer（子进程） | Docker 容器（每实例一镜像） | Python 进程 + pytest + asyncio | Web API + BullMQ 队列 + Worker |
| 判分函数 | ICL Evaluator（规则/Judge） | 测试脚本 + F2P/P2P 解析 | Metric（score/threshold/reason） | Evaluator（LLM judge / code / decision） |
| 结果存储 | predictions/results/summary 文件 | logs/报告 JSON/CSV | TestRun（内存+磁盘+平台） | ClickHouse + Postgres + S3 |

**记住这个抽象，后面每个框架都按"四要素 + 数据流"来读。**

## 一、OpenCompass：配置驱动的"评测任务编排器"

### 1.1 模块地图（`opencompass/opencompass/`）

| 模块 | 职责 | 关键文件 |
|---|---|---|
| `cli/` | 命令行入口，组装 infer/eval 两阶段任务 | `cli/main.py`（518 行） |
| `partitioners/` | 把"模型×数据集"笛卡尔积切成任务分片 | `base.py`、`naive.py`、`num_worker.py`、`size.py` |
| `runners/` | 执行任务：本地子进程 / Slurm / DLC / rjob | `local.py`、`slurm.py`、`dlc.py` |
| `tasks/` | 任务实现：推理任务、评测任务、流式评测守护 | `openicl_infer.py`（179 行）、`openicl_eval.py`（572 行）、`openicl_eval_watch.py` |
| `openicl/` | 评测核心：dataset reader、prompt template、retriever、inferencer、evaluator | `icl_inferencer/`、`icl_evaluator/`、`icl_prompt_template.py` |
| `evaluator/` | 新式评测器：LLM judge、级联、数学、VLMEvalKit | `generic_llm_evaluator.py`、`cascade_evaluator.py` |
| `summarizers/` | 扫描 results → 解析 → 聚合成表（CSV/Markdown） | `default.py`（`_pick_up_results`/`_format_table`） |
| `models/` `datasets/` `configs/` | 模型/数据集实现与预制配置（3300+ 文件的大头在这） | `configs/models`、`configs/datasets` |
| `registry.py` | 全部组件的注册表 | mmengine `Registry` |

注册表是理解 OpenCompass 的钥匙（`registry.py`）：

```python
PARTITIONERS / RUNNERS / TASKS / MODELS / LOAD_DATASET
TEXT_POSTPROCESSORS / DICT_POSTPROCESSORS / EVALUATORS
ICL_INFERENCERS / ICL_RETRIEVERS / ICL_DATASET_READERS
ICL_PROMPT_TEMPLATES / ICL_EVALUATORS / METRICS
```

配置文件里写 `type=` 字符串，框架通过 `build_from_cfg` 反射构建对象——**"配置即插件"**。

### 1.2 执行流程（从 `opencompass config.py` 到 summary）

```text
cli/main.py::main()
 ├─ 1. parse_args()                # --models/--datasets/--mode/--work-dir/--reuse/--debug...
 ├─ 2. get_config_from_arg(args)   # 合并命令行与配置文件 → mmengine Config
 ├─ 3. work_dir/<timestamp>/       # 目录：configs/ predictions/ results/ summary/ logs/
 │     └─ cfg.dump(configs/<ts>_<pid>.py)   # 配置快照（复现凭据）
 ├─ 4. mode=all/infer：
 │     fill_infer_cfg()   # 默认 NumWorkerPartitioner + LocalRunner + OpenICLInferTask
 │     partitioner = PARTITIONERS.build(...)
 │     tasks = partitioner(cfg)      # 按模型/数据集切分任务
 │     runner  = RUNNERS.build(...)
 ├─ 5. mode=all/eval：
 │     fill_eval_cfg()    # 默认 NaivePartitioner + LocalRunner + OpenICLEvalTask
 │     eval_tasks / eval_runner
 ├─ 6. 运行：
 │     infer_runner(infer_tasks)
 │     eval_runner(eval_tasks)
 │     （若 eval task 是 OpenICLEvalWatchTask，则 eval 线程与 infer 并行——流式评测）
 └─ 7. 可选：结果 station 持久化（--station-path）
```

**注意两个关键设计**：

1. **任务 = 子进程 + 命令行模板**。`LocalRunner` 不直接调 Python 函数，而是为每个任务生成 `python tasks/openicl_infer.py <cfg_path>` 命令，用 `CUDA_VISIBLE_DEVICES=` 前缀控制 GPU（`runners/local.py::get_command_template`），再用 `ThreadPoolExecutor` 并发跑子进程。好处：GPU 隔离天然、崩溃不传染；代价：进程间通信只能靠文件。
2. **infer 与 eval 完全分离**：推理产物落盘为 predictions JSON，评测阶段只读文件 → 可单独重跑评测（`-m eval -r latest`），这也是**降低成本**的关键设计。

### 1.3 推理任务内部（`tasks/openicl_infer.py`）

```text
OpenICLInferTask.run()
 ├─ for model_cfg, dataset_cfgs:          # 模型 × 数据集
 │   ├─ build_model_from_cfg(model_cfg)  # 实例化模型（HF/API/vLLM/LMDeploy）
 │   ├─ build_dataset_from_cfg(dataset_cfg)
 │   ├─ out_path = predictions/<model>/<dataset>.json
 │   ├─ if exists: continue              # 断点续跑的关键
 │   └─ _inference():
 │        ├─ ICL_PROMPT_TEMPLATES.build(...)   # ice_template / prompt_template
 │        ├─ ICL_RETRIEVERS.build(...)         # few-shot 检索器
 │        ├─ ICL_INFERENCERS.build(...)        # 生成式/困惑度/chat/agent/attack 等
 │        └─ inferencer.inference(retriever, prompts, output_json_filepath, filename)
```

`openicl/icl_inferencer/` 下有 ~20 种 inferencer：`GenInferencer`、`PPLInferencer`、`ChatInferencer`、`ChatMLInferencer`、`AgentInferencer`、`AttackInferencer`、`Parallel` 变体等。**推断**：它抽象的是"如何把 dataset 样本变成模型的调用序列"，所以每种任务形态（生成/打分/多轮/攻击）对应一个 inferencer。

### 1.4 评测任务内部（`tasks/openicl_eval.py`）

```text
OpenICLEvalTask.run()
 ├─ for model×dataset:
 │    ├─ out_path = results/<model>/<dataset>.json；存在则跳过
 │    └─ _score():
 │         ├─ _load_and_preprocess_test_data()   # 重新构建 dataset，取 golden
 │         ├─ _load_predictions()                # 读 predictions JSON
 │         ├─ 若含 rollout → _sum_rollout()      # 多次采样聚合
 │         ├─ ICL_EVALUATORS.build(eval_cfg.evaluator)  # 规则/Judge/代码/级联
 │         │     + TEXT_POSTPROCESSORS 抽取答案
 │         └─ _save_results() + dump_details（逐样本对错）/ extract_rate
```

评测器两大类（`openicl/icl_evaluator/` + `evaluator/`）：

- **规则类**：`icl_em_evaluator`（精确匹配）、`icl_hf_evaluator`（accuracy/rouge/sacrebleu/squad）、`code_evaluator`、`aucroc`、`bpc` 等；
- **Judge 类**：`icl_judge_evaluator`、`evaluator/generic_llm_evaluator.py`。`GenericLLMEvaluator` 值得单独读：它 `build_inferencer()` 内部再建一个 judge inferencer，`score()` 逐条构造裁判 prompt、调 judge 模型、`_judge_postprocess` 解析输出，`default_judge_cfg()` 提供默认裁判模型配置——**"用模型评模型"的完整闭环**。

### 1.5 汇总（`summarizers/default.py`）

`DefaultSummarizer` 不去读任务对象，而是**扫描 `results/` 目录**：`_pick_up_results()` → `_calculate_group_metrics()`（分组求均值）→ `_format_table()`（CSV/Markdown）→ `_output_to_file()`。这是一种"文件即数据库"的松耦合：任务只要能产出约定格式，就能被汇总。

### 1.6 可复现与成本机制（源码里能直接看到的）

| 机制 | 实现位置 | 作用 |
|---|---|---|
| 配置快照 | `cli/main.py` `cfg.dump(output_config_path)` | 复现时用当时的配置，不依赖当前代码 |
| 时间戳目录 | `work_dir/<YYYYmmdd_HHMMSS>` | 多次实验互不覆盖 |
| 产物跳过 | infere/eval 里 `if osp.exists(out_path): continue` | 断点续跑、增量补跑 |
| `--reuse` | `cli/main.py` 解析 reuse 指向历史目录 | eval-only / 复用旧结果 |
| 任务分片 | partitioners（num_worker/size/sub_*） | 大实验可拆到多卡/多机 |

### 1.7 扩展点（二次开发）

1. **加数据集**：实现 loader 并 `@LOAD_DATASET.register_module()`，或在 config 里用 `custom_dataset` 快速接入；
2. **加模型**：`@MODELS.register_module()` 实现 `generate/chat/get_ppl` 接口；
3. **加评测器**：`@ICL_EVALUATORS.register_module()`（规则）或继承 `BaseEvaluator`（Judge 类）；
4. **加 inferencer/summarizer**：对应 registry 注册；
5. **贡献路径**：configs 目录里加配置是 PR 门槛最低的入口。

### 1.8 局限（从代码结构暴露出来的）

- **子进程 + 文件通信**：单任务粒度过粗时（如 1 个模型 × 100 个数据集）调度不均衡；中断后只能整任务重跑（虽然有产物跳过缓解）。
- **配置漂移**：config 快照是好的，但模型/数据集的实现代码没有版本锁定，跨版本复现仍可能不一致。
- **Judge 成本与稳健性**：`GenericLLMEvaluator` 逐条调用，样本量大时成本线性增长；答案抽取（`TEXT_POSTPROCESSORS`）是常见失败点（抽取失败会被误判为答错）。
- **榜单语义**：CompassRank 与本地 configs 可能不同步，跨榜对比要核对配置。

## 二、SWE-bench：容器化的"修复判定器"

### 2.1 模块地图（`swebench/`）

| 模块 | 职责 | 关键文件 |
|---|---|---|
| `types.py` | 数据结构：`SWEbenchInstance`、`TestSpec` | 全文仅 ~60 行，先读 |
| `harness/` | 判分执行器（核心） | `run_evaluation.py`（853 行）、`grading.py`、`docker_utils.py`、`reporting.py`、`infra_failure.py` |
| `image_builder/` | 每实例镜像的构建/拉取 | `docker_utils.py`、build specs |
| `inference/` | 生成预测（mini-SWE-agent 等） | `run_inference.py`、`make_datasets.py` |
| `cli/` | `swebench` 子命令（eval/infer/report/images/dataset） | `cli/` |
| `resources/` | 各仓库的环境脚本、log parser、测试命令 | 按 repo 组织 |
| `collect/` `task/` `submit/` | 数据采集、任务定义、提交 | — |

### 2.2 核心数据结构：TestSpec

`types.py` 的 `TestSpec` 是判分的"完整契约"：

```python
@dataclass
class TestSpec:
    instance_id: str
    image: str                 # 预构建镜像名
    eval_script_list: list[str]# 逐行执行的测试命令（已注入退出码记录）
    repo: str
    version: str               # 环境版本
    FAIL_TO_PASS: list[str]    # 必须由 fail 变 pass 的测试
    PASS_TO_PASS: list[str]    # 必须保持 pass 的测试
    log_parser: str            # 用哪个日志解析器（按 repo 区分）
    eval_type: str             # 判分类型（决定用哪套报告逻辑）
    image_assets: dict         # 多模态任务需要的二进制资产
    @property
    def eval_script(self): ... # 拼成 "#!/bin/bash\nset -uxo pipefail\n" + commands
```

`harness/utils.py::make_test_spec(instance)` 把 HF 数据集的一行转成 TestSpec：`FAIL_TO_PASS`/`PASS_TO_PASS` 可能是 JSON 字符串 → `json.loads`；`eval_script` 经过 `parse_eval_script` + `record_test_exit_code`（在每个测试命令后记录 `$?`）。

### 2.3 判分主流程

```text
swebench eval <dataset> -p preds --run-id X
 └─ harness/run_evaluation.py::main()
      ├─ load instances（HF 数据集/本地 task-repo）
      ├─ get_dataset_from_preds()          # 只取有预测的实例；支持 -i 子集
      ├─ (可选) _build_before_eval()       # 提前构建/拉取镜像
      ├─ run_instances(..., max_workers)   # ThreadPool 并发
      │    └─ run_instance(test_spec, pred)
      │         ├─ 若 report.json 已存在 → 直接返回（缓存）
      │         ├─ create_container()       # 镜像不存在则 pull；容器 tail -f 保活
      │         ├─ copy patch.diff 进容器
      │         ├─ 依次尝试 GIT_APPLY_CMDS（失败后 git reset 再来）
      │         ├─ verify reverse apply   # 处理"命令失败但补丁已应用"的边界
      │         ├─ 写入/执行 eval_script  → test_output.txt
      │         └─ get_eval_report()       # 解析测试日志 → resolved
      └─ reporting.make_run_report()        # 汇总 resolved/completed/error/infra_failure
```

### 2.4 判分逻辑（`harness/grading.py`）

```text
get_eval_report(test_spec, prediction, test_log_path)
 ├─ patch 为空 → patch_is_None=True
 ├─ get_logs_eval(test_spec, log)      # 按 log_parser 解析测试状态 map
 │    └─ 解析失败 → classify_logs() 标记 infra_failure（环境问题 vs 模型问题）
 ├─ get_eval_tests_report(eval_status_map, eval_ref, eval_type)
 │    ├─ compute_fail_to_pass()        # F2P 通过率
 │    └─ compute_pass_to_pass()        # P2P 通过率
 └─ get_resolution_status(report)
      └─ 仅当 F2P=100% 且 P2P=100% → "resolved"（FULL）
```

`report_map` 的字段很有信息量：`patch_is_None`、`patch_exists`、`patch_successfully_applied`、`resolved`、`infra_failure`、`infra_failure_reason`、`tests_status`——**它明确区分了"模型错"和"环境坏"**，这是大规模评测最重要的设计之一。

### 2.5 镜像与结构缓存

- 每个实例一个镜像（`swebench` 的 `image` 字段），构建逻辑在 `image_builder/`；镜像只在第一次构建/拉取，后续复用；
- 运行结果按 `logs/run_evaluation/<run_id>/<model>/<instance>/report.json` 缓存，**run_id 是缓存键的一部分**——这正是"换 patch 必须换 run_id"的源码级原因；
- `docker_utils.py` 管理构建、运行、清理（`remove_containers.py`），容器命名 `sweb.eval.<instance>.<run_id>`，避免并发冲突；`cap_add=["SYS_ADMIN"]` 是为浏览器类测试的沙箱需要。

### 2.6 推理侧（`swebench infer`）

`inference/` 与 `swebench infer` 子命令负责"生成 patch"：读取实例的 `problem_statement`、`base_commit`，用 agent（默认 mini-SWE-agent）在容器/环境中操作，产出预测文件。**关键点：推理与判分在代码上完全解耦**，所以你可以用任何 agent 生成预测，再用官方 harness 判分——这是 SWE-bench 被广泛采用的原因。

### 2.7 局限

- 环境复现成本高（镜像、依赖、arm 支持实验性）；log_parser 是按 repo 手写的，测试输出格式变化会导致解析失败；
- 测试本身的覆盖偏差：修复正确但测试没覆盖 → 不算 resolved；测试本身不稳定 → 误判（infra_failure 缓解但不根治）；
- 可被针对性优化（reward hacking），这也是后续 SWE-Bench Pro 等出现的背景。

## 三、DeepEval：把评测变成"pytest 插件 + 指标生命周期"

### 3.1 模块地图（`deepeval/deepeval/`）

| 模块 | 职责 |
|---|---|
| `evaluate/` | 入口：`evaluate()`、`assert_test()`、执行器 `execute/`、结果类型、控制台报告 |
| `metrics/` | 指标实现 + `base_metric.py` 基类（349 行） |
| `test_case/` | `LLMTestCase`、`ConversationalTestCase`、`MCP` 等数据结构 |
| `test_run/` | 测试运行管理（聚合、缓存、磁盘持久化、平台上报、hooks） |
| `plugins/plugin.py` | **pytest 插件**（`[tool.poetry.plugins."pytest11"]`） |
| `tracing/` | `@observe`、span、trace-scoped 评测 |
| `dataset/` `synthesizer/` | 数据集与合成数据 |
| `red_teaming/` `guardrails/` | 红队与护栏 |
| `benchmarks/` | MMLU/HumanEval 等内置基准（10 行调用） |
| `cli/` | `deepeval test run` 等命令（Typer） |

### 3.2 入口与执行流

```text
deepeval test run test_*.py
 └─ pytest 启动（deepeval.plugins.plugin 注册）
      └─ 测试函数里：assert_test(test_case, [metrics])
           └─ evaluate/evaluate.py::assert_test()
                ├─ validate_assert_test_inputs()
                ├─ AsyncConfig（max_concurrent=100, throttle=0）
                │  DisplayConfig / ErrorConfig / CacheConfig（由环境变量控制）
                ├─ 若 golden/plugin 场景 → 从当前 trace 取用例（trace-scoped）
                └─ 执行（异步优先）→ 任一 metric 失败 → AssertionError（flaky 用例只告警）
```

`evaluate()`（批量、非 pytest 场景）与 `assert_test()` 共用执行器：

```text
evaluate/execute/e2e.py::a_execute_test_cases()
 ├─ with_expectation_evaluators()      # 把"预期"自动转成 evaluator metric
 ├─ asyncio.Semaphore(async_config.max_concurrent)  # 并发闸门
 ├─ global_test_run_cache_manager      # 指标级缓存（相同 input+metric 不重算）
 ├─ 拆分 BaseMetric / BaseConversationalMetric
 ├─ 遍历用例 → 构造 task → 每个 (case, metric) 调 _execute_metric()
 │    └─ _common.py::_execute_metric()
 │         ├─ try metric.measure(test_case, _show_indicator=..., _in_component=...)
 │         ├─ TypeError → 回退 metric.measure(test_case)（兼容旧签名）
 │         ├─ MissingTestCaseParamsError → skip（按 error_config）
 │         ├─ 其他异常 → ignore_errors ? 记 error : 抛出
 │         └─ 结果写回 metric（score/reason/success/cost/tokens）
 └─ 收集 TestResult → TestRun 聚合 → 控制台报告 / 本地存储 / 可选平台上报
```

`evaluate/execute/` 下还有 `agentic.py`（按 span/trace 评 Agent 轨迹）、`loop.py`（trace 级评测循环）、`trace_scope.py`（trace 作用域断言）——对应"端到端评测"和"轨迹评测"两种模式。

### 3.3 指标生命周期（`metrics/base_metric.py`）

`BaseMetric` 是全部指标的契约，字段就是一套"评测结果模型"：

```python
threshold / score / reason / success / strict_mode
async_mode / verbose_mode / include_reason
evaluation_cost / input_tokens / output_tokens
skipped / flaky / requires_trace
model / eval_mode / confidence
```

方法契约：

```text
measure(test_case) -> float        # 抽象：必须实现
a_measure(test_case) -> float      # 抽象：异步实现
is_successful() -> bool            # score >= threshold；threshold 为空则 None
_accrue_cost() / _accrue_tokens()  # 成本核算
```

`__init_subclass__` 会给子类方法自动挂 tracing（`observe_methods(cls)`）——**指标执行本身可观测**。`BaseConversationalMetric`（多轮）、`BaseArenaMetric`（对战）是另两套变体。

**自定义指标**：继承 `BaseMetric`，实现 `measure`/`a_measure`，设置 `threshold/score/reason`，`is_successful()` 父类逻辑即可工作。这就是 DeepEval 最容易做二次开发的地方。

### 3.4 test run 与 pytest 集成

- `test_run/test_run.py`：`TestRun` 聚合所有用例与指标分数，`TestRunManager` 负责重置/创建/更新/保存到临时文件（`TEMP_FILE_PATH`）、计算通过率；支持 sqlite 本地存储与平台（Confident AI）上报。
- pytest 插件（`plugins/plugin.py`）在测试会话结束（`on_test_run_end`）触发汇总/上报，`deepeval test run` 是它的包装命令。
- 缓存：`CacheConfig(write_cache, use_cache)` + `global_test_run_cache_manager`，按 (input, metric) 命中缓存，避免重复调用 judge。

### 3.5 局限

- Judge 成本与确定性：指标本质是 LLM 调用，分数有方差，需重复评估与校准；
- 指标选择依赖经验：指标语义重叠（如 answer relevancy 与 GEval），阈值没有默认科学值；
- pytest/平台耦合：插件与平台上报是可选但会引入环境依赖（`.env` 自动加载是常见坑）；
- Agent 轨迹评测依赖 tracing 埋点质量，埋点缺失会静默降级。

## 四、Langfuse：事件驱动的"可观测数据平台 + 在线评测流水线"

### 4.1 总体架构（monorepo）

```text
web/        Next.js：UI + 公开 API（ingestion / OTLP / prompts / datasets / scores）
worker/     BullMQ Worker：异步消费队列（ingestion、otel、eval、experiment、export...）
packages/shared/  领域逻辑：ingestion pipeline、OTel processor、evals、repositories、PromptService
packages/shared/prisma/        Postgres schema（业务元数据）
packages/shared/clickhouse/    ClickHouse migrations（可观测数据）
```

存储四件套（自托管时都要起）：**Postgres**（项目/数据集/评测规则/任务状态）、**ClickHouse**（traces/observations/scores/events/run-items）、**Redis/Valkey**（队列/缓存）、**S3/MinIO**（事件与多模态附件）。

### 4.2 数据模型：两类数据分开存

**ClickHouse（高写入、列存、可聚合成表）**——核心三张表（`migrations/canonical/0001~0003`）：

| 表 | 关键列 | 引擎要点 |
|---|---|---|
| `traces` | id, timestamp, name, user_id, metadata(Map), session_id, input/output(ZSTD), project_id, public, bookmarked, tags, event_ts, is_deleted | `ReplacingMergeTree(event_ts, is_deleted)`，按 `toYYYYMM(timestamp)` 分区，PK `(project_id, toDate(timestamp))` |
| `observations` | id, trace_id, parent_observation_id, type, start/end_time, name, level, status_message, model_parameters, usage_details(Map UInt64), cost_details(Map Decimal), total_cost, prompt_name/version | 同上，按 start_time 分区，TYPE 进主键 |
| `scores` | id, timestamp, trace_id, observation_id, name, value(Float64), source, comment, data_type, string_value, config_id, queue_id | ReplacingMergeTree；按 name 进主键（便于按指标聚合） |

设计要点：
- **ReplacingMergeTree + event_ts + is_deleted**：同一 id 的多次写入按时间取最新，删除用 `is_deleted` 标记——软删除 + 幂等写入；
- **metadata/usage/cost 用 Map**：半结构化字段无需迁移；input/output 用 ZSTD 压缩；
- 新增 `events` 表（migrations 0039+）+ `dataset_run_items` 表：事件溯源与实验宽表，是 v4 的新方向。

**Postgres（Prisma，业务事务）**：`Dataset`/`DatasetItem`/`DatasetRuns`、`Prompt`（版本/标签/依赖）、`EvalTemplate`/`Evaluator`/`EvaluatorVersion`、`EvaluationRule`、`JobConfiguration`/`JobExecution`、`ScoreConfig`、`AnnotationQueue`、`Dashboard`/`Monitor`、组织与 API Key 等。

### 4.3 写入主链路（SDK → 存储）

```text
SDK/OTel ──HTTP──▶ web: /api/public/ingestion.ts
 ├─ 认证与 scope（projectId/orgId/plan；ingestion 是否被暂停）
 ├─ 限流（RateLimitService，按 "ingestion" 维度）
 ├─ 批次校验（authorizeIngestionBatch）
 └─ processEventBatch()（packages/shared/src/server/ingestion/processEventBatch.ts）
      ├─ zod 逐事件校验（非法事件进 errors，不影响其它事件）
      ├─ 丢弃 SDK_LOG 事件
      ├─ sortBatch()：按依赖排序（observation 依赖 trace 等）
      ├─ 按 eventBodyId 分组（同实体合并，减少存储/队列次数）
      ├─ 写 S3（事件原文，fileKey） 
      └─ 入队 IngestionQueue（worker 异步消费）
worker: IngestionService 消费队列
 ├─ 解析事件 → 幂等写入 ClickHouse（traces / observations / scores）
 └─ 失败重试/死信（BullMQ）
```

**设计取舍**：API 只做"接收 + 校验 + 落盘 + 入队"，重计算全部异步化——写入快、可抗峰值、可重放。

**OTel 链路**（`/api/public/otel/v1/traces`）：

```text
OTLP ResourceSpans
 └─ shared/server/otel/OtelIngestionProcessor.ts
      ├─ processToEvent(resourceSpans)      # OTel span → Langfuse 事件（trace-create + observation-create）
      ├─ processSpan()/createTraceEvent()/createObservationEvent()
      └─ 属性映射（gen_ai.*、usage、model、media、attributes）
worker/features/otel-ingestion/processOtelEvents.ts
      ├─ processor.processToEvent() 再执行一次（同一批）
      ├─ IngestionService.createEventRecord()（补全 trace 级属性）
      ├─ scheduleObservationEvals()（若有评测规则）
      └─ IngestionService.writeEventRecord()（SDK 版本满足时写 events 表）
```

### 4.4 评测流水线（评测即"规则 + 队列 + Evaluator"）

数据模型：**Evaluator（可版本化的评分器）→ EvaluationRule（目标 + 过滤器 + 采样 + 变量映射）→ JobExecution（执行记录）→ Score（结果）**。

```text
事件写入（trace/observation）
 └─ fetchObservationEvalRules(projectId)           # 读取启用的规则
      └─ scheduleObservationEvals()                 # 匹配过滤器/采样 → 生成 JobExecution
           └─ 入队 EvalExecutionQueue
worker: evalService.ts
 ├─ createEvalJobs()        # 校验 trace/observation 存在、规则匹配、去重（确定性 job id）
 ├─ runLLMAsJudgeEvaluation()
 │    ├─ extractVariablesFromTracingData()   # 从 trace/observation 取值填变量
 │    ├─ executeLlmEvaluator()               # llmEvaluatorExecution.ts
 │    │    ├─ buildEvalMessages()            # compileEvalPrompt（变量插值）
 │    │    ├─ generateLlmText()              # 一次模型调用（OTel 记录 span/成本）
 │    │    └─ validateEvalOutputResult()     # 按 outputDefinition 校验 {score, reasoning}
 │    ├─ toNormalizedScores()                # 分数归一化（布尔/类别/数值）
 │    └─ 写 scores 表（source=API/EVAL，config_id、job_execution_id）
 ├─ code evaluator：executeCodeBasedEvaluation() → 本地子进程 / AWS Lambda 沙箱
 ├─ decision model evaluator：runDecisionModelEvaluation()
 └─ completeEvalExecution()                  # 更新 JobExecution 状态与指标
```

`llmEvaluatorExecution.ts` 里有个值得学习的细节：**给模型看的 schema 用 `scoreExplanation` 而不是 `reasoning`**（思考型模型会把 `reasoning` 当草稿而丢掉分数），输出后再映射回 `{score, reasoning}` 契约——这是"评测器也要为模型行为设计"的好例子。

### 4.5 数据集与实验（Dataset → Experiment）

```text
Dataset / DatasetItem（输入 + 期望输出 + 版本）
 └─ SDK: langfuse.run_experiment(name, data, task, evaluators)
      ├─ ExperimentRunner 逐条执行 task（自动 trace，带 dataset-run 元数据）
      ├─ item 级/run 级 evaluator 打分 → scores
      └─ 结果写入 dataset_run_items / experiment 视图
UI: Compare Experiments（按 dataset run 对比多个 prompt/模型版本）
```

源码里能看到的关键约束：
- `packages/shared/src/features/experiments/utils.ts`：`validateDatasetItem()` / `normalizeDatasetItemInput()`——**dataset item 的输入必须能映射到 prompt 变量**，单变量时允许裸字符串并自动包装；
- `worker/src/features/experiments/scheduleExperimentEvals.ts`：实验产生的 observation 也会走同一套 `scheduleObservationEvals`，保证"线上评测"与"离线实验"共用评分逻辑；
- Prompt 变量与 dataset 字段的对齐是实验能否跑通的第一道坑（对应执行手册里的 dataset 结构问题）。

### 4.6 Prompt 管理（`PromptService`）

`getPrompt()` → 先查缓存（`getCachedPrompt`），未命中 `findPrompt()` 查库/解析引用，`resolvePrompt()` 递归解析 `@@@langfusePrompt:name=version@@@` 依赖，`buildAndResolvePromptGraph()` 建依赖图，`invalidateCache()` 按 epoch token 失效。**Prompt 是带版本的资产，不是字符串常量**——这是 Langfuse 相对"自己写个 dict"的本质区别。

### 4.7 局限与注意点

- 基础设施重（4 个存储组件），自托管成本高；ClickHouse 有最终一致性（ReplacingMergeTree 去重依赖 merge/FINAL），刚写入的数据在分析查询里可能延迟可见；
- 评测规则/采样/去重逻辑复杂（`evalService.ts` 1800 行），排障要会看 JobExecution 状态机；
- 多租户缓存（prompt/eval config/epoch）设计精巧但容易成为 bug 源；
- 成本控制需要自己配（采样、过滤、模型选择）。

## 五、横向对比：四个框架的设计哲学

| 维度 | OpenCompass | SWE-bench | DeepEval | Langfuse |
|---|---|---|---|---|
| 本质 | 评测任务编排器 | 修复判定执行器 | 评测单测框架 | 可观测数据平台 + 评测流水线 |
| 执行模型 | CLI → 任务分片 → 子进程 | CLI → 线程池 → Docker 容器 | pytest → async → metric 调用 | Web API → 队列 → worker |
| 隔离方式 | 进程 + 文件产物 | 容器（每实例一镜像） | Python 进程 | 队列 + 沙箱（code eval） |
| 判分原语 | evaluator（规则/Judge） | 测试脚本 + F2P/P2P | metric（score/threshold） | evaluator（LLM/code/decision） |
| 结果存储 | JSON + CSV/Markdown | JSON 报告 + CSV | TestRun（内存/磁盘/平台） | ClickHouse + Postgres + S3 |
| 复现凭据 | config 快照 | 镜像 + run_id | 用例代码 + 缓存 | trace 全量 + 版本化 prompt/evaluator |
| 扩展点 | registry 组件 | 镜像/任务仓库/log parser | 自定义 Metric | Evaluator/规则/数据源 |
| 典型失败模式 | 抽取失败、配置漂移 | 环境坏、日志解析失败 | judge 方差、阈值不当 | 队列积压、规则不匹配 |
| 二次开发难度 | 中（组件多但模式统一） | 中（Docker 依赖重） | 低（继承 BaseMetric） | 高（TS monorepo + 多存储） |

### 可以带走的 5 个设计洞见

1. **"配置/数据即资产"**：OpenCompass 快照 config、SWE-bench 锁镜像、Langfuse 版本化 prompt/evaluator——评测可信的前提是"可追溯的输入"。
2. **判分必须区分"模型错"和"环境坏"**：SWE-bench 的 `infra_failure`、Langfuse 的 JobExecution 状态、DeepEval 的 `error/skipped`、OpenCompass 的独立 eval 阶段，都在解决同一个问题。
3. **评测要能和"生成"解耦**：SWE-bench 的 infer/eval 分离、OpenCompass 的 infer/eval 分离、Langfuse 的在线/离线共用 evaluator——解耦后才能用不同 agent、不同模型、不同时间点复用判分。
4. **异步与队列是规模化关键**：Langfuse 的 event-sourcing 与 DeepEval 的 async semaphore 是同一个问题的两种规模解法。
5. **评测本身要可观测**：DeepEval 给 metric 自动加 tracing、Langfuse 给 judge 调用记 span、SWE-bench 记录每实例日志——否则评测出错你无法归因。
